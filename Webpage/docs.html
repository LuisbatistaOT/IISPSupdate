1. Overview

This tool orchestrates Windows patching in controlled project runs. It scans target servers for available KB updates, lets operators choose update selections, executes installs with background jobs, and verifies outcomes after reboot.

2. Technology & Architecture

Core stack

  • Backend: ASP.NET Core MVC + API (.NET 8)
  • Database: SQL Server via EF Core
  • Background processing: Hangfire with SQL storage
  • Automation: PowerShell hosted with System.Management.Automation
  • Update execution: PSWindowsUpdate and Invoke-WUJob on targets
  • Auth model: IIS Windows Authentication (Anonymous disabled)

High-level flow

  • Create project and import servers
  • Run pre-flight WinRM checks and scan for KB candidates
  • Select KBs and save selection
  • Start run (immediate or scheduled)
  • Monitor progress in live run page and Hangfire
  • Verify install outcomes and export reports

3. Prerequisites

  • IIS host reachable by operators (intranet)
  • .NET Hosting Bundle installed on IIS host
  • SQL Server reachable by application identity
  • Hangfire tables and app schema deployed
  • PowerShell/PSWindowsUpdate available for orchestration behavior
  • Network connectivity from app host to targets on WinRM ports
Keep pre-production and production environments with separate SQL databases and appsettings.

4. Identity, Auth, and Service Accounts

IIS authentication

  • Enable Windows Authentication
  • Disable Anonymous Authentication

App pool identity

  • Use a managed service account or dedicated domain service account (recommended)
  • Avoid using personal user accounts for production app pools
  • Grant minimum SQL rights needed for app + Hangfire operations

Kerberos and naming

  • Use FQDNs for targets whenever possible
  • Validate SPN resolution and DNS correctness
  • Avoid relying on TrustedHosts as a primary domain strategy

5. Deployment and Hosting

  • Publish app from build host: dotnet publish -c Release
  • Copy publish folder to IIS site path
  • Verify IIS site binding and app pool assignment
  • Confirm static path /Webpage/index.html loads (dashboard landing)
If you get HTTP 500 immediately, check IIS stdout logs and Windows Event Viewer first.

6. Database Setup

  • Apply schema in correct order (or EF migration script) with cascade-safe constraints
  • Verify permissions for app identity on target DB
  • Set proper connection strings for app DB and Hangfire storage
  • Use retry-enabled SQL options and sensible pool sizing

Known good checks

  • App starts and homepage loads without DB exception
  • Hangfire dashboard loads and shows storage initialized
  • Projects can be created and persisted

7. WinRM and Target Server Prep

Target host prerequisites

  • WinRM service running and listener present (5985 and/or 5986)
  • Firewall allows inbound WinRM from app host network
  • Remote management policy applied consistently (GPO preferred)
  • PowerShell remoting enabled (Enable-PSRemoting)

Connectivity tests (from app host)

  • Resolve-DnsName target.fqdn
  • Test-NetConnection target.fqdn -Port 5985
  • Test-WSMan target.fqdn
  • Enter-PSSession -ComputerName target.fqdn -Authentication Kerberos
Scan success does not guarantee installability. If pre-flight fails, updates are intentionally blocked.

8. How to Use the App

Typical operator workflow

  • Create project and import server list
  • Run pre-flight and scan
  • Review candidates and select KBs
  • Analyze selection and start run
  • Track progress on run details page
  • Retry failed targets or export reports

Scheduled runs

  • Set future UTC schedule during run creation
  • Cancel before execution from Run Details via Cancel scheduled run

9. Hangfire Operations

  • Dashboard URL: /hangfire
  • Queues include: scan, install, verify, default
  • Use dashboard to inspect processing, retries, failures, and server health
  • App now supports explicit API/UI cancellation for scheduled runs before start

10. Debugging and Logs

Where to look first

  • Run Details page server-level status and log tail
  • Hangfire job details and exception traces
  • IIS stdout logs and Windows Event Viewer
  • SQL connectivity/authentication errors in app logs

Quick diagnostic matrix

  • Build/publish issues: verify SDK, restore, and publish artifacts
  • HTTP 500 at startup: appsettings, SQL auth, missing runtime dependency
  • Run fails before install: WinRM/Kerberos/network path issues

11. Common Issues and Fixes

AWS VPC/Subnet routing issue (critical)

  • Symptom: Test-NetConnection target -Port 5985/5986 fails from app host, but target local WinRM config is correct
  • Root cause: no route/ACL path between source and target subnets/VPCs
  • Fix: update route tables + SG/NACL rules for source to target WinRM path and return traffic

SQL login failures for app pool identity

  • Symptom: cannot open database for IIS APPPOOL\... or service identity
  • Fix: grant DB login/user rights or move app pool to approved domain service account

Connection pool exhaustion

  • Symptom: timeout waiting for pooled connection
  • Fix: tune Hangfire worker count, SQL pool size, and retry settings

JSON cycle serialization

  • Symptom: object cycle detected on scan endpoint
  • Fix: return flattened DTOs for API responses (already implemented)

Multiple cascade path DB errors

  • Symptom: SQL migration create table/foreign key fails
  • Fix: enforce restricted delete behaviors in EF model and regenerate script

WinRM trusted hosts / auth confusion

  • Symptom: default credentials fail over HTTP
  • Fix: prefer domain Kerberos with FQDN and valid SPN/name path; verify network reachability first

12. Recommended Hardening

  • Use dedicated service account and least privilege access model
  • Restrict admin roles in app and audit run actions
  • Enforce TLS for app access and secure SQL transport where feasible
  • Standardize WinRM configuration through GPO baselines
  • Add environment-specific backup/restore and DR runbooks
